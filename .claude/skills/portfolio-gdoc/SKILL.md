# 기획서 → 포트폴리오 Google 문서 변환

부속 파일: `style-spec.json`(서식 값의 유일한 기준), `base.html`(원고 머리), `postfix.py`(보정), `check_format.py`(검증), `diagrams.md`(도식 절차, 도식 승인 후에만 읽음), `reference.md`(보정 내역·함정, 손으로 고칠 때만 읽음).

## 1. 기준
- 기준 양식: [RSPRullet 게임 컨셉 기획서 (포트폴리오)](https://docs.google.com/document/d/1lC3-zZ-fL7MkuTD7gSIgSz4jUrFBvNuAVOnQZEteSI4/edit). 글자 크기·색·간격·들여쓰기·표 값은 `style-spec.json`만 본다. **기준 문서를 다시 분석하지 않는다.**
- `base.html`의 `<style>`은 spec 값을 옮겨 적은 사본이다. spec을 바꾸면 `base.html`의 같은 값도 함께 고친다.
- 사용자가 다른 템플릿을 지정할 때만 그 문서를 docx로 내보내 XML에서 값을 뽑아 `style-spec.json` 사본을 만든다(`read_doc`은 표 테두리·셀 여백을 돌려주지 않는다).
- 서식 원칙(값은 spec):
  - 단락 앞뒤 간격 = 그 단락의 글자 크기. 목차 항목·빈 줄·구분선 단락은 0, 표 안은 적용하지 않는다.
  - 정렬은 모두 왼쪽, 가운데는 표 머리행 셀 안 단락에만(표·행 범위로 보내면 표 앞 단락까지 바뀐다).
  - 목차 제목은 "목차"만 쓴다.
- 원고 규칙:
  - **긴 항목 분리**: "항목명: 내용"이 한 줄(spec `label_wrap` 기준. 1단계 약 38자, 2단계 약 36자)을 넘으면 항목명(굵게, 콜론 없음)만 남기고 내용은 하위 항목으로 내린다.
  - **마침표 분리**: 한 단락에 문장이 여럿이면 문장마다 단락을 나눈다. 목록은 둘째 문장부터 글머리 없는 연속 단락(그 단계 글자 위치에 맞춤). 쉼표에서는 나누지 않는다. 제목·목차·표 안은 제외. 원고에서 빠뜨린 곳은 보정 스크립트가 처리한다.
  - **절 사이 빈 줄**: 절 제목 앞에 빈 줄 한 줄. 장 제목 바로 다음 절(사이에 단락이 없을 때)과 이미 빈 줄이 있는 곳만 제외한다. 장 작성 의도 단락 뒤에 오는 첫 절에도 넣는다. 이 빈 줄의 글자 크기는 절 제목 크기로 보정된다.

## 2. 사전 확인
- Google Drive·Docs 커넥터 연결 확인. 없으면 연결을 요청하고 시작하지 않는다.
- 원본은 `RSPRulletDocs` 스페이스의 해당 기획서. **대상 페이지 하나만** 본문 위주로 읽는다(`responseFields` 등으로 필드 최소화). 하위 페이지 목록은 "세부 기획서 목록"을 적을 때만 조회하고, 실제로 조회한 문서만 적는다.
- `google-workspace` 스킬은 평소 읽지 않는다. 필요한 규칙은 아래 "Google 커넥터 필수 규칙"이고, 여기에 없는 오류가 날 때만 그 스킬의 `references/docs.md`에서 해당 절을 찾아 읽는다.

### Google 커넥터 필수 규칙
- 새 문서는 Drive `create_file`(`contentMimeType: "text/html"`, `textContent`에 원고)로 만든다. 이후 수정은 Docs `update_doc`.
- 위치는 UTF-16 단위(이모지는 2 이상), 본문은 1부터. 삽입·삭제는 뒤 위치를 밀므로 높은 위치부터 보낸다. **쓰기 뒤에는 이전 위치를 재사용하지 않고 다시 읽는다.**
- `replaceAllText`만 있는 묶음이 아니면 `writeControl.requiredRevisionId`에 마지막 쓰기 이후 읽은 `revisionId`를 넣는다. 400이면 다시 읽고 다시 만든다(가드 없이 재시도 금지).
- 탭이 여럿이면 모든 `location`·`range`에 `tabId`를 넣는다.
- `read_doc` 결과는 크므로 파일로 받아 스크립트로만 요약한다. 내용 확인만 필요하면 Drive `read_file_content`(`includeComments: true`)를 쓴다(위치 계산에는 쓰지 않는다).

## 3. 내용 정제
- 뺀다: "구현 키워드", 미정·확정 예정 등 작업 상태 표시, "(비활성)"·"~가 생길 때까지"처럼 이슈 처리에 따라 바뀌는 특정 시점의 상태 표기(설계된 요소는 남기고 상태 표기만 지운다), 검토 중인 후보안. 원본에 없는 값은 만들지 않는다.
- 남긴다: 내부 메모(예: "구현 방식은 각 개발 이슈에서 정합니다"). 기획서와 최신 코드의 차이를 맞추는 일은 이 스킬 범위가 아니다.
- 올린다: 기획 의도와 설계 원칙.
  - **기획 의도**: 게임 디자인상 의도(그 규칙·시스템을 왜 그렇게 설계했는지)가 필요한 절에만 "기획 의도:" 항목으로 쓴다. 장·절을 왜 적었는지(작성 의도)를 기획 의도로 쓰지 않는다.
  - **작성 의도**: 장·절·소제목이 무엇을 정리하는지는 제목 바로 다음 줄에 본문 단락(`<p>`)으로 쓴다.
    예: "2.3 상태 다이어그램" 다음 줄 → "분기가 많은 진행 흐름을 한눈에 볼 수 있도록 상태와 전환 조건을 그림으로 정리합니다."
- 장 구성: 목차 → 1 프로젝트 개요 → 2 시스템 기획 → 3 컨텐츠 기획 → 4 프로젝트 운영. 제목은 "📝 1. 프로젝트 개요"처럼 이모지 + 번호, 이모지는 겹치지 않게.
- **도식화**: 흐름(진행 순서·분기·순환)이나 구성 요소 간 관계를 설명하는 절, 특히 원본에 머메이드가 있던 곳은 도식 후보다. 후보는 도식화 브리핑(`diagrams.md` 0번 형식)으로 승인받는다. **승인되지 않은 곳의 머메이드는 "[A] ➔ [B]" 텍스트 흐름으로 바꾼다.**

## 4. 작업 순서
**멈추는 곳: 도식화 브리핑 승인 한 번, 도구 실패·범위 변경**(그 밖에는 중간 보고 없이 진행, `behavior-guidelines.md` 8장 예외).

1. **정제와 도식화 브리핑**: 원본을 정제하고, 도식 후보가 있으면 브리핑 후 승인을 기다린다. 후보가 없으면 바로 다음으로.
2. **원고 업로드**: `base.html`의 `<style>` 머리를 그대로 쓰고 본문만 작성해(5장) Drive `create_file`의 `textContent`에 **한 번만** 쓴다(로컬 저장 금지, 같은 원고를 두 번 쓰지 않는다. 예외는 5장 굵게 복원뿐). 승인된 도식 위치에는 `[도식 삽입: 파일명]` 표시 단락을 넣는다.
3. **보정**: `read_doc` 결과(파일)에 `python -I postfix.py <파일>`을 돌려 나온 `requests`·`writeControl`을 `update_doc`에 그대로 보낸다.
   - 출력이 커서 한 번에 보내기 어려우면 `--max N`(30 이상)을 붙인다. 보낸 뒤 다시 읽고 같은 명령을 반복하면 남은 요청만 나온다(stderr의 "남은 요청"이 0이 될 때까지). 삽입 묶음은 스크립트가 항상 마지막에 둔다.
4. **검증**: Drive `download_file_content`(`exportMimeType`: docx)를 부른다. 결과는 base64라 크다.
   - 결과가 파일로 저장됐으면 `python -I check_format.py <그 파일>`(스크립트가 base64를 직접 푼다).
   - 결과가 대화에 그대로 들어왔으면 **base64를 Write로 옮겨 적지 않는다**(같은 분량을 한 번 더 출력하게 된다). 대신 문서를 다시 읽어 `postfix.py`를 돌리고 요청이 0개면 보정 항목은 통과로 본다. `check_format.py` 검증은 미실행으로 보고한다.
   - "OK"면 끝. ✗가 남으면 `python -I postfix.py <다시 읽은 파일> --extra-only`로 그 부분만 다시 보낸다. 그래도 남는 것만 `reference.md`를 보고 손으로 고친다. PDF 내보내기는 페이지 없음 문서에서 실패하므로 쓰지 않는다.
5. **도식(승인된 경우)**: `diagrams.md` 절차를 따른다. PNG 확인이 반복되므로 원고 작업이 길었으면 새 세션으로 나눠 진행하는 것을 제안한다.
6. **최종 보고**(`[작업 결과]` 한 번): 문서 링크(같은 문서면 링크 유지 명시), 정제 내용, 검증 결과, 미검증 항목(화면 모양은 직접 못 봄), 만든 시험·임시 문서(사용자가 원할 때만 휴지통으로).

- 금지: 서식을 수백 건의 수정 요청으로 덧입히기, 같은 요청 JSON을 두 번 이상 읽기(`update_doc`에 넘기려면 한 번은 읽어야 한다), 큰 `read_doc` 결과를 대화로 읽기, docx base64를 대화로 읽거나 옮겨 적기.

## 5. HTML 작성 규칙
- **`<style>`에 글꼴(`font-family`)·`font-weight`를 넣지 않는다.** 글꼴 규칙이 있으면 `<b>`가 모두 사라진다. 글꼴은 보정에서 문서 전체에 한 번 적용한다. 그래도 굵게가 사라졌을 때만 예외로 원고를 scratchpad에 파일로 저장해 `postfix.py ... --bold-src <원고.html>`로 복원한다(못 찾은 구절은 stderr). 원고 전체를 다시 출력하는 비용이 들므로 위 금지 규칙으로 먼저 막는다.

| 서식 | HTML |
|---|---|
| 문서 제목 | 첫 `<h1>` (보정에서 TITLE로 바뀜) |
| 목차 | `<h1>목차</h1>` + `<li class="toc">` |
| 장 제목 / 구분선 | `<hr>` 다음 `<h1>` (구분선 분리는 보정에서) |
| 절 제목 | `<h2>` |
| 본문 | 문장마다 `<p>` |
| 소제목 | `<p class="lab"><b>핵심 목표</b></p>` |
| 빈 줄 | `<p class="sp"><br></p>` (소제목 앞, 장 끝) |
| 목록 | `<ul><li>` (2단계 이하 들여쓰기는 보정에서) |
| 항목명 (한 줄 이내) | `<li><b>항목명:</b> 설명</li>` |
| 항목명 (한 줄 초과) | `<li><b>항목명</b><ul><li>설명</li></ul></li>` |
| 목록 문장 분리 | `<li>첫 문장.</li>` 다음 `<p class="cont">둘째 문장.</p>` (들여쓰기는 `base.html`과 보정에서) (번호 목록은 번호가 다시 시작될 수 있어 검증으로 확인) |
| 표 | `<table>`, 머리행 `<tr class="h">`, 마지막 행 `<tr class="z">`, 첫 열 `<td class="l">`, 끝 열 `<td class="r">`. 머리행·첫 열은 `<b>`로 감싼다. 열 너비·셀 단락·굵게는 보정에서 |

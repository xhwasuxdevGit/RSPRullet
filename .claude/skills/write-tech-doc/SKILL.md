# 기술문서 작성 및 Jira 연결

## 1.실행 조건
- 기능 개발 완료 시 **먼저 사용자에게** 다음을 묻는다:
  "이번 기능을 Confluence 기술 문서에 새로 작성하거나 기존 문서에 반영할까요? Jira 문서화 이슈도 생성할까요?"
- **명시적 승인 전에는 Confluence/Jira 쓰기 작업을 하지 않는다.**
- 사용자가 작성만 요청한 경우 우선 초안을 제시한다. 게시나 Jira 이슈 생성은 별도 승인 범위에 따라 수행한다.
- 문서 작성은 기능 구현이 아니므로 `behavior-guidelines.md`의 구현 브리핑을 적용하지 않는다. 위 Confluence/Jira 승인 절차는 그대로 유지한다.
- 이슈 구현 세션과 분리된 새 세션에서 수행한다. 시작 자료는 PR 본문의 문서 변경 메모와 Jira 결과 코멘트다.

## 2.자료 수집
1. PR 본문의 "문서 변경 메모"를 읽는다(`gh pr view <번호> --json body`). 메모가 있으면 갱신 범위의 기준으로 삼고, Jira 이슈와 코드는 메모만으로 문장을 쓸 수 없는 부분만 확인한다.
   - 메모가 없으면 실제 Jira 이슈(`RSP-번호`)의 요구사항·완료 조건과 변경 코드(주요 클래스·인터페이스, 데이터 흐름, 테스트 결과)를 확인한다.
2. `gh pr diff <번호> --name-only`의 변경 스크립트에서 클래스 이름을 뽑아, `기술 문서` 폴더(ID `2424853`, 하위 폴더 포함) 안에서 CQL `ancestor = 2424853 AND type = page AND text ~ "클래스명"`으로 대상 문서를 찾는다.
   - 검색 결과를 메모의 대상 문서와 비교하고, 검색에만 걸린 문서가 있으면 사용자에게 알린다.
   - 대상 문서는 목차(outline)만 본다. 본문은 5단계에서 Claude가 갱신하기로 정한 문서만 읽는다.
   - 검색에 걸리는 문서가 없으면 `기술 문서` 폴더와 하위 폴더(예: `UI 및 화면 표시`)의 페이지 목록을 조회한다.
3. 기획 문서는 새 문서를 쓰거나 "관련 문서" 표에 새 기획서를 넣을 때만 `기획 문서` 폴더의 하위 페이지 목록을 조회한다. 같은 주제의 세부 기획서가 있으면 세부 기획서를 기준으로 삼고, 문서의 규칙 링크도 세부 기획서로 건다.
4. 초안을 쓰기 전에 기존 문서에 추가할지, 새 문서로 작성할지 검토해 사용자에게 제안하고 확인받는다.
   - 후보: 관련 기존 문서에 장 추가 / 새 문서 1개 / 기능별로 새 문서 여러 개로 분리
   - 판단 기준: 기존 문서의 제목·목적 범위에 들어가는가, 같은 시스템을 다루는가,
     이후 이슈에서 따로 갱신될 가능성(변경 시점이 다른가), 문서 하나의 분량
   - 후보별 장단점을 짧게 비교하고 추천안과 이유를 제시한다. 확인 전에는 초안을 쓰지 않는다.
5. 기존 문서 갱신이면 목차와 코드 변경만으로 갱신 범위(문서 수, 문서별로 고칠 장)를 정리하고, 본문을 읽기 전에 누가 고칠지 사용자에게 확인받는다.
   - 다음 중 하나에 해당하면 작업량이 큰 갱신으로 보고, 사용자가 직접 고치는 방식을 권장안으로 제시한다: 갱신할 문서가 3개 이상이다, 한 문서에서 고칠 장이 4개 이상이다, 문서를 나눠 하위 에이전트로 처리해야 할 분량이다.
   - 사용자가 직접 고치기로 하면 Claude는 대상 문서를 Markdown으로 한 번 읽고 문서별 수정 안내서를 작성한다.
     - 위치는 소제목 이름과 앞 문장의 첫머리로 짚는다. 장 번호는 적지 않는다(번호가 다시 매겨지면 안내서와 어긋난다).
     - 바꿀 문장은 "현재 문장(첫머리) → 새 문장"으로, 새 표 행은 열 순서대로 셀 내용을, 새 장·소제목은 전문으로 적는다.
     - 기존 표의 열 너비·글자 크기는 같은 표 기존 행을 따르라고 적는다.
   - 사용자가 고친 뒤 확인을 요청하면 Markdown으로 다시 읽어 안내서 반영 여부와 중복을 확인한다.

## 3.제목 규칙
- 형식: `NN. 기술문서 제목` (`NN`은 `01`, `02`처럼 두 자리 숫자). 번호는 Confluence 페이지의 실제 제목에 포함한다.
- **신규 작성:** 게시 직전에 `기술 문서` 폴더와 하위 폴더 전체의 실제 페이지 목록을 조회한다. 제목 앞 `NN.`의 최댓값에 1을 더한 번호를 사용하고, 같은 번호가 없는지 확인한다.
- 신규 문서는 `기술 문서`의 하위 폴더 중 하나에 만든다. 문서가 따르는 기획서와 다루는 대상으로 고른다.

  | 폴더 | 넣는 문서 (기준 기획서) |
  |---|---|
  | 공통 기반 | 여러 시스템이 함께 쓰는 설정 데이터, 화면 연결·상태 조회 |
  | 카드와 승패 판정 | 카드·카드풀·배분·공개 상태, 판정과 체력 정산 (02 코어 규칙) |
  | 게임 진행 | 진행 단계(상태 기계), 라운드 진행 흐름, 라운드 전환 (02 코어 규칙, 06 라운드와 게임 진행) |
  | 아이템 | 아이템 데이터·보유·지급, 아이템 단계 진행 (05 아이템) |
  | 딜러 AI | 딜러의 카드 분배·아이템 판단 (04 딜러 AI) |
  | UI 및 화면 표시 | 상태를 언제 무엇으로 보여 줄지, 버튼·입력·팝업·안내 (03 UI·UX, 07 튜토리얼) |
  | 연출 및 애니메이션 | 시간에 따라 움직이는 연출, 캐릭터 애니메이션, 글자·렌더 표시 설정 (08 연출·아트·사운드) |

  - 두 폴더에 걸치면 문서의 주된 책임으로 고른다. 표시와 연출처럼 성격이 다른 내용이 크게 섞이면 4-4의 분리 후보로 보고한다.
  - 맞는 폴더가 없으면 새 폴더를 만들지 않고 사용자에게 폴더 추가를 제안한다.
- **기존 문서 갱신:** 제목과 번호를 유지한다. 다른 문서의 번호를 임의로 바꾸지 않는다.
- 기술 문서가 아닌 다른 영역(기획, 회의록 등)에는 이 규칙을 적용하지 않는다.

## 4.작성 원칙
### 4-1. 내용
- 구조(구성 요소와 책임, 참조 방향)와 프로세스(데이터 흐름, 상태 전환, 호출 순서)를 기능 구현 관점에서 쓴다. 제약·예외는 이 둘에 영향을 주는 것만 쓴다.
- 쓰지 않는 것: 수치·설정값·문구(어디에 있고 어떻게 읽히는지만 쓰고 값은 원본에 맡긴다), 기획 배경·규칙의 이유, 메서드 코드의 줄 단위 옮김, 다른 문서(기획서·기술 문서·Rules)의 상세 규칙, 완료·처리된 이슈.
- 짧은 문장으로 쓰되 기술적으로 중요한 내용은 빠뜨리지 않는다.
- 실제 코드와 설계에 근거한다. 확인되지 않은 구현·테스트를 사실처럼 쓰지 않고, 원본 문서와 충돌하면 따로 보고한다.
- 게임 규칙 용어로 쓰고, 처음 나올 때 코드 이름을 함께 적는다. 예: 라운드 진행(`RoundProgress`)

### 4-2. 장 구성
- 문서 맨 위에 목차 매크로(`toc`, 제목 단계 3까지)를 두고 아래 순서로 쓴다. 내용이 없는 장은 생략하고 번호를 당긴다.
  1. 목적: 관련 Jira 이슈를 적는다. 바로 아래 "관련 문서" 표(문서: 번호와 이름을 정확히, 링크 / 이 문서와의 관계: 한 줄)에 참조 문서를 모두 모은다. 본문에서는 링크를 다시 걸지 않고, 장을 짚을 때만 글자로 적는다(예: 아이템 세부 기획서 4-3장).
  2. 구성 요소: 클래스마다 스크립트 경로와 맡는 책임 한 줄. 메서드는 나열하지 않는다.
  3. 주요 클래스와 메서드: 클래스마다 소제목(게임 용어 + 코드 이름)과 표(구분: 메서드 / 프로퍼티 / 이벤트 순서 / 이름 / 하는 일: 한 줄). 다른 클래스가 부르는 공개 멤버만 적고, 비공개 메서드는 흐름 이해에 필요한 것만 적는다. 호출 관계는 흐름 장에만 쓴다. 예외: 설정 데이터 문서처럼 값을 어디서 읽는지가 문서의 목적이면 "부르는 곳" 열을 둔다.
  4. 설계 의도: 원칙만 쓴다.
  5. 대안 비교: 이후 구현이 따라야 하는 핵심 설계 선택(기획서 "구현 키워드"의 데이터 구조·알고리즘·설계 패턴 등)만 둔다. 선택마다 소제목 → 주요 대안 1~2개 비교 표 → "선택:" → 이유(최대 3줄). 이름·폴더 위치처럼 구조가 변하지 않는 선택은 비교하지 않는다. 예: 셔플 — 피셔-예이츠 vs 무작위 정렬(OrderBy)
  - 문서별 장(흐름·화면 연결·제약 등): 흐름은 실제 호출되는 메서드를 순서대로 적는다. 예: [다음 라운드] 버튼 → `PhaseButtonsUI.OnNextRound()` → `GameFlowRunner.StartNextRound()` → `RoundProgress.AdvanceRound()` → 씬 다시 불러오기
  - 테스트: 실제 수행한 테스트와 미검증 항목.
  - 변경 이력: 변경마다 최대 3줄로 짧게.
- 장 아래 소제목에는 `장번호-순번.` 번호를 붙이고(예: 5-2. 책임 분리), 본문에서는 "6-2장 메서드 호출 순서"처럼 짚는다.

### 4-3. 서식
- 본문은 글머리 하나에 문장 하나를 두고, 앞 문장을 보충하는 문장은 하위 글머리로 둔다. 장 제목·표 셀·변경 이력 표는 예외다.
- 표와 코드 예시는 이해에 도움이 될 때만 쓴다. 표가 있는 문서는 HTML로 쓴다(markdown은 표 속성을 지정할 수 없다).
- 표 양식: 표 너비 760, 모든 셀 `font-size: 12px`, 열 너비는 내용에 맞게 지정하고 합을 표 너비와 같게 한다.

### 4-4. 기존 문서 갱신과 검사
- 기존 양식(표 너비·열 너비·셀 글자 크기, 셀 안 줄바꿈, 소제목 번호와 제목 문구, 문단 나눔)을 바꾸지 않는다. 이 원칙과 다른 기존 양식을 발견해도 고치지 않고 보고만 한다.
- 기존 표에 행을 넣을 때는 같은 표 기존 행의 열 너비와 글자 크기를 쓴다. 4-3 본문 서식은 새로 쓰는 문장에만 적용한다.
- 문서를 쓰거나 고칠 때마다 확인한다.
  - 반복된 설명이 없도록 한곳으로 모은다.
  - 별도 기능으로 묶어 새 문서로 나눌 수 있거나 목차의 소제목(`N-M.`)이 15개를 넘으면 분리 후보로 보고한다. 목차를 볼 때 함께 세고, 분리는 사용자 확인 후 별도 작업으로 한다.

## 5.게시와 Jira 작업
1. 작성 초안을 사용자에게 보여주고 신규/갱신 대상과 게시 승인을 확인한다.
2. 승인 후 rsprullet 사이트에 연결된 Atlassian 커넥터(`CLAUDE.md` "지침 위치")로 Confluence 페이지를 생성 또는 갱신한다.
   - 기존 문서는 초안 본문(draft)을 HTML로 한 번 읽어 그 본문을 기준으로 작업한다. 읽은 초안이 발행본과 다르면 이전 편집 잔여물이 있는 것이므로 사용자에게 알리고 확인받는다.
   - 커넥터가 노드 단위 수정을 지원하면 바뀐 노드만 노드 ID로 교체·삽입·삭제하고, 바꾸지 않을 노드는 보내지 않는다. 같은 기준 노드에 여러 노드를 넣을 때는 넣을 순서대로 보낸다.
   - 노드 단위 수정을 지원하지 않으면 본문 전체를 교체하되, 읽어 온 HTML에서 변경할 장만 고치고 나머지는 그대로 보낸다.
   - 읽을 때 받은 스냅숏 토큰을 함께 보내고, 토큰이 오래됐다는 응답이 오면 다시 읽고 변경을 다시 적용한다. 같은 요청을 그대로 다시 보내지 않는다.
   - 저장 후 목차로 장 구성을 확인하고, 새로 넣은 문장의 순서와 중복은 Markdown으로 다시 읽어 변경한 장을 확인한다. 전체 문서를 반복해서 읽지 않는다.
3. Jira 문서화 이슈 생성은 **별도 승인된 경우에만** 수행한다. 관련 개발 이슈와 문서 링크를 연결한다.
4. 실제 문서 URL, Jira 이슈 키 및 수행 결과를 보고한다.
5. 기존 개발 이슈의 Done 전환은 별도 승인과 완료 조건 검증 없이 하지 않는다.

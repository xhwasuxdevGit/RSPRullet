# 기술문서 작성 및 Jira 연결

## 1.실행 조건
- 기능 개발 완료 시 **먼저 사용자에게** 다음을 묻는다:
  "이번 기능을 Confluence 기술 문서에 새로 작성하거나 기존 문서에 반영할까요? Jira 문서화 이슈도 생성할까요?"
- **명시적 승인 전에는 Confluence/Jira 쓰기 작업을 하지 않는다.**
- 사용자가 작성만 요청한 경우 우선 초안을 제시한다. 게시나 Jira 이슈 생성은 별도 승인 범위에 따라 수행한다.
- 문서 작성은 기능 구현이 아니므로 `behavior-guidelines.md`의 구현 브리핑을 적용하지 않는다. 위 Confluence/Jira 승인 절차는 그대로 유지한다.

## 2.자료 수집
1. 실제 Jira 이슈(`RSP-번호`)의 요구사항과 완료 조건을 조회한다.
2. 변경된 코드, 주요 클래스·인터페이스, 데이터 흐름, 테스트 결과를 확인한다.
3. Confluence `기술 문서` 폴더와 그 하위 폴더(예: `UI 및 화면 표시`)의 페이지 목록을 조회하고, 해당 기능과 관련된 개별 기술 문서를 확인한다.
   - 이 단계에서는 관련 기술 문서의 목차(outline)만 본다. 본문은 5장에서 Claude가 갱신하기로 정한 문서만 읽는다.
4. Confluence `기획 문서` 폴더의 하위 페이지 목록을 조회하고, 기능과 관련된 기획 문서를 확인한다. 같은 주제의 세부 기획서가 있으면 세부 기획서를 기준으로 삼고, 문서의 규칙 링크도 세부 기획서로 건다.
5. 초안을 쓰기 전에 기존 문서에 추가할지, 새 문서로 작성할지 검토해 사용자에게 제안하고 확인받는다.
   - 후보: 관련 기존 문서에 장 추가 / 새 문서 1개 / 기능별로 새 문서 여러 개로 분리
   - 판단 기준: 기존 문서의 제목·목적 범위에 들어가는가, 같은 시스템을 다루는가,
     이후 이슈에서 따로 갱신될 가능성(변경 시점이 다른가), 문서 하나의 분량
   - 후보별 장단점을 짧게 비교하고 추천안과 이유를 제시한다. 확인 전에는 초안을 쓰지 않는다.
6. 기존 문서 갱신이면 목차와 코드 변경만으로 갱신 범위(문서 수, 문서별로 고칠 장)를 정리하고, 본문을 읽기 전에 누가 고칠지 사용자에게 확인받는다.
   - 다음 중 하나에 해당하면 작업량이 큰 갱신으로 보고, 사용자가 직접 고치는 방식을 권장안으로 제시한다: 갱신할 문서가 3개 이상이다, 한 문서에서 고칠 장이 4개 이상이다, 문서를 나눠 하위 에이전트로 처리해야 할 분량이다.
   - 사용자가 직접 고치기로 하면 Claude는 본문을 읽지 않고 문서별 수정 안내서를 작성한다.
     - 위치는 장 번호·소제목과 앞 문장의 첫머리로 짚는다.
     - 바꿀 문장은 "현재 문장(첫머리) → 새 문장"으로, 새 표 행은 열 순서대로 셀 내용을, 새 장·소제목은 전문으로 적는다.
     - 기존 표의 열 너비·글자 크기는 같은 표 기존 행을 따르라고 적는다.
   - 사용자가 고친 뒤 확인을 요청하면 목차와 고친 장만 다시 읽어 확인한다.

## 3.제목 규칙
- 형식: `NN. 기술문서 제목` (`NN`은 `01`, `02`처럼 두 자리 숫자). 번호는 Confluence 페이지의 실제 제목에 포함한다.
- **신규 작성:** 게시 직전에 `기술 문서` 폴더와 하위 폴더 전체의 실제 페이지 목록을 조회한다. 제목 앞 `NN.`의 최댓값에 1을 더한 번호를 사용하고, 같은 번호가 없는지 확인한다.
- 화면 표시·UI 기능 문서는 `기술 문서/UI 및 화면 표시` 폴더에 만든다.
- **기존 문서 갱신:** 제목과 번호를 유지한다. 다른 문서의 번호를 임의로 바꾸지 않는다.
- 기술 문서가 아닌 다른 영역(기획, 회의록 등)에는 이 규칙을 적용하지 않는다.

## 4.작성 원칙
- 기능 구현 관점에서 구조(구성 요소와 책임, 참조 방향)와 프로세스(데이터 흐름, 상태 전환, 호출 순서)를 설명하는 데 집중한다. 제약·예외 처리는 구조와 프로세스에 영향을 주는 것만 쓴다.
  - 구체적인 수치·설정값·문구는 나열하지 않는다. 값이 어디에 있고 어떤 흐름으로 읽히는지만 쓰고, 값 자체는 원본(기획서, 설정 에셋)에 맡긴다.
- 장 순서: 1. 목적(바로 아래 "관련 문서" 표) → 2. 구성 요소 → 3. 주요 클래스와 메서드 → 4. 설계 의도 → 5. 대안 비교 → (흐름·화면 연결·제약 등 문서별 장) → 테스트 → 변경 이력
  - 설계 의도에는 원칙만 쓴다.
  - 대안 비교는 비교 단위마다 소제목을 두고, 비교 표 → "선택:" → 이유(최대 3줄) 순서로 쓴다.
  - 해당 내용이 없는 장은 생략하고 번호를 당긴다.
  - 장 아래 소제목에는 `장번호-순번.` 형식의 번호를 붙인다. 예: 3-1. 게임 진행 `GameFlow`, 5-2. 책임 분리. 본문에서 짚을 때는 "6-2장 메서드 호출 순서"처럼 쓴다.
- 문서 맨 위(1. 목적 위)에 Confluence 목차 매크로(`toc`, 제목 단계 3까지)를 둔다.
- 구성 요소마다 스크립트 경로, 클래스, 그 기능을 이루는 주요 공개 메서드·프로퍼티·이벤트를 적는다.
  - "주요 클래스와 메서드" 장에 클래스마다 소제목(게임 용어 + 코드 이름, 예: 라운드 진행 `RoundProgress`)을 두고, 그 아래 표로 정리한다.
  - 표의 열: 구분(메서드 / 프로퍼티 / 이벤트) / 이름 / 하는 일(한 줄) / 부르는 곳. 행은 구분 순서대로 놓는다.
  - "구성 요소" 표의 역할 칸은 그 클래스가 맡는 책임을 한 줄로만 쓰고 메서드를 나열하지 않는다. 메서드 단위 설명은 "주요 클래스와 메서드"에만 둔다.
  - 비공개 메서드는 흐름을 이해하는 데 필요한 것만 적는다.
- 흐름(호출 순서, 상태 전환)을 설명할 때는 실제로 호출되는 메서드를 순서대로 적는다.
  - 예: [다음 라운드] 버튼 → `PhaseButtonsUI.OnNextRound()` → `GameFlowRunner.StartNextRound()` → `RoundProgress.AdvanceRound()` → 씬 다시 불러오기
- 근거와 설명은 구조를 이해하는 데 꼭 필요한 것만 쓴다. 기획 배경, 규칙의 이유는 쓰지 않고, 메서드 안의 코드를 줄 단위로 옮겨 적지 않는다. 짧은 문장으로 쓰되 기술적으로 중요한 내용은 누락하지 않는다.
- 본문 서식: 문장 하나마다 줄을 바꾸고, 문장 하나를 글머리 기호 하나에 둔다.
  - 한 글머리에 두 문장 이상 넣지 않는다.
  - 앞 문장을 보충하는 문장은 하위 글머리로 둔다.
  - 장 제목, 표 셀, 변경 이력 표는 이 서식을 적용하지 않는다.
- 설명은 게임 규칙의 용어로 쓰고, 처음 나올 때 코드 이름을 함께 적는다. 예: 라운드 진행(`RoundProgress`)
- 표와 코드 예시는 이해에 도움이 될 때만 사용한다.
  - 신규 문서의 표도 기존 기술 문서의 표 양식을 따른다: 표 너비 760, 모든 셀 `font-size: 12px`, 열 너비는 내용에 맞게 지정해 합이 표 너비와 같게 한다.
  - 표가 있는 문서는 HTML로 작성한다. markdown으로는 표 속성을 지정할 수 없다.
- 기존 문서를 갱신할 때는 기존 양식을 바꾸지 않는다: 표 너비·열 너비·셀 글자 크기, 셀 안 줄바꿈, 소제목 번호와 제목 문구, 문단 나눔.
  - 위 작성 원칙과 다른 기존 양식(열 너비 합이 표 너비와 다른 표, 번호 없는 소제목 등)을 발견해도 고치지 않고 보고만 한다.
  - 기존 표에 행을 넣을 때는 같은 표 기존 행의 열 너비와 글자 크기를 그대로 쓴다.
  - 문장 하나당 줄바꿈 등 본문 서식 규칙은 새로 쓰는 문장에만 적용한다.
- 핵심 설계 선택(데이터 구조, 알고리즘, 설계 패턴 등 기획서 "구현 키워드"에 해당하는 항목)은 대안 비교 장에 주요 대안 1~2개와 장단점을 간단히 비교하고, 최종 선택 이유를 최대 3줄로 명시한다.
  - 예: 설정 데이터 — ScriptableObject vs 코드 상수 vs JSON / 셔플 — 피셔-예이츠 vs 무작위 정렬(OrderBy)
  - 비교는 이후 구현이 따라야 하는 선택에만 둔다. 이름·폴더 위치처럼 바꿔도 구조가 변하지 않는 선택은 비교하지 않는다.
- 다른 문서(기획서, 다른 기술 문서, Rules)에 있는 상세 규칙은 반복하지 않는다.
  - 참조하는 문서는 "1. 목적" 바로 아래 "관련 문서" 표 한곳에 모은다. 열은 문서(번호와 이름을 정확히, 링크)와 이 문서와의 관계(한 줄)다.
  - 본문 각 장에서는 같은 문서의 링크를 다시 걸지 않는다. 특정 장을 짚어야 할 때만 문서 이름과 장 번호를 글자로 적는다 (예: 아이템 세부 기획서 4-3장).
- 실제 코드와 설계에 근거해 작성한다. 확인되지 않은 구현이나 테스트를 사실처럼 쓰지 않고, 원본 문서와 충돌하는 부분은 별도로 보고한다.
- 필요 시 다음 항목을 포함한다: 목적과 관련 Jira 이슈, 관련 문서 표, 실제 수행한 테스트와 미검증 항목, 변경 이력.
  - 변경 이력에 담을 주요 변경 사항은 간곃하게 작성하고 최대 3줄을 넘어가지 않는다.
- 문서가 수정될때마다 검사할 내용은 다음과 같다.
  - 중복된 내용이 없느지 검토하고 한곳으로 모아 반복된 설명을 문서에 담지 않는다.
  - 별도의 기능으로 묶어 새로운 기술 문서로 분리가 가능하다면 사용자에게 보고하고 브리핑을 제안한다.
- 구현이 완료되었거나 처리된 이슈는 기술 문서에서 언급하지 않는다 

## 5.게시와 Jira 작업
1. 작성 초안을 사용자에게 보여주고 신규/갱신 대상과 게시 승인을 확인한다.
2. 승인 후 rsprullet 사이트에 연결된 Atlassian 커넥터(`CLAUDE.md` "지침 위치")로 Confluence 페이지를 생성 또는 갱신한다.
   - 기존 문서는 초안 본문(draft)을 HTML로 한 번 읽어 그 본문을 기준으로 작업한다. 읽은 초안이 발행본과 다르면 이전 편집 잔여물이 있는 것이므로 사용자에게 알리고 확인받는다.
   - 커넥터가 노드 단위 수정을 지원하면 바뀐 노드만 노드 ID로 교체·삽입·삭제하고, 바꾸지 않을 노드는 보내지 않는다. 같은 기준 노드에 여러 노드를 넣을 때는 넣을 순서대로 보낸다.
   - 노드 단위 수정을 지원하지 않으면 본문 전체를 교체하되, 읽어 온 HTML에서 변경할 장만 고치고 나머지는 그대로 보낸다.
   - 읽을 때 받은 스냅숏 토큰을 함께 보내고, 토큰이 오래됐다는 응답이 오면 다시 읽고 변경을 다시 적용한다. 같은 요청을 그대로 다시 보내지 않는다.
   - 저장 후 목차로 장 구성을 확인하고, 새로 넣은 문장의 순서와 중복은 변경한 장만 다시 읽어 확인한다. 전체 문서를 반복해서 읽지 않는다.
3. Jira 문서화 이슈 생성은 **별도 승인된 경우에만** 수행한다. 관련 개발 이슈와 문서 링크를 연결한다.
4. 실제 문서 URL, Jira 이슈 키 및 수행 결과를 보고한다.
5. 기존 개발 이슈의 Done 전환은 별도 승인과 완료 조건 검증 없이 하지 않는다.

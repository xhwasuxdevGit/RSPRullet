# Jira 이슈 기반 개발 시작

> `jira-workflow` 스킬(`.claude/skills/jira-workflow/SKILL.md`)의 Phase 1~3을 실행하고 Phase 4로 넘기는 절차다. 이 세션에서 아직 읽지 않았다면 먼저 읽는다. 승인 시점과 정책은 해당 스킬과 `behavior-guidelines.md`를 따르며 여기서 반복하지 않는다.

## 입력
- Jira 이슈 키 `RSP-<번호>` 또는 작업 요청 내용을 받는다.
- `$ARGUMENTS`가 있으면 이슈 키를 추출한다. 실제 Jira 키는 브랜치 slug가 아니다.

## 1. Jira 이슈 확인 (Phase 1)
1. 이슈 키가 있으면 Atlassian MCP로 제목, 유형, 설명, 완료조건, 상태, 담당자, 관련 링크를 한 번 조회한다. 실패하면 중단하고 알린다.
2. 이슈 키가 없으면 요청 내용으로 관련 기존 이슈를 JQL 검색하고, 후보를 제시해 대상 이슈를 확인받는다.
3. 관련 이슈가 없으면 요청 내용을 기준으로 신규 이슈를 생성할지 묻는다.
4. 생성하기로 하면 `.claude/skills/jira-workflow/issue-template.md`로 초안을 작성한다. 배경/목적이 확인되지 않으면 질문하고, 초안 승인 후에만 생성한다. 생성 후 실제 이슈 키를 보고한다.

## 2. 조사 (읽기 전용)
1. 실행 모드(`behavior-guidelines.md` 4장)를 정하고 작업을 **설계 / 기능 개발 / 혼합**으로 분류한다.
2. Confluence는 필요한 경우에만 관련 문서를 조회한다 (QUICK: 조회하지 않음 / STANDARD: 이슈가 기획서를 근거로 하거나 화면 배치·수치·규칙이 필요할 때 / DEEP: 관련 문서 조회).
   - 먼저 CQL `text ~ "RSP-NN"`으로 이슈 키를 언급한 문서를 찾는다. 기획서의 미결 사항·갱신 항목에서 이 이슈로 넘긴 결정을 확인하기 위해서다.
   - 공통: Jira 이슈의 근거가 컨셉 기획서여도 같은 주제의 세부 기획서가 있으면 세부 기획서를 기준으로 한다. 제목 검색으로 대신하지 않고 폴더의 하위 페이지 목록을 확인한다.
   - 설계 시: Confluence `기획 문서` 폴더의 하위 페이지 목록을 조회하고, 이슈 내용에 맞는 개별 기획 문서만 읽는다.
   - 개발 시: 요구사항은 `기획 문서` 폴더에서, 기존 구현은 `기술 문서` 폴더에서 확인한다. 각 폴더와 그 하위 폴더의 페이지 목록을 조회하고 이슈 내용에 맞는 개별 문서만 읽는다.
     - 목록 조회만으로 기존 구현을 확인했다고 보지 않는다. 연결 지점이 속한 기존 시스템의 기술 문서도 관련 장을 읽는다.
   - 문서는 outline(목차)을 먼저 보고, 본문은 Markdown으로 읽어 관련 장만 본다.
   - 맞는 문서를 특정할 수 없으면 후보 문서 제목을 제시하고 사용자에게 확인한다.
   - 링크를 안다는 이유만으로 읽었다고 주장하지 않는다. 문서 접근 실패, 문서 간 충돌, 코드와의 불일치는 알리고 추측으로 확정하지 않는다. 문서가 없는 기능은 Jira 요구사항과 실제 코드를 확인한다.
3. 수정 대상 코드와 직접 호출 관계, 관련 Scene/Prefab을 **읽기 전용으로** 확인하고 범위·영향 파일·검증 계획을 정리한다.
   - 완료 조건이 기존 시스템과 맞물리거나 에픽의 첫 이슈이면, 키워드 검색으로 찾은 연결 지점(매개변수, 메서드, "○○ 이슈에서 연결" 주석)을 브리핑에 `파일:줄`로 적는다.
   - Scene 기반 작업이면 `unity-guidelines.md`에따라 Scene 폴더를 결정한다. 확정할 수 없으면 사용자에게 확인한다.
4. `git status`와 현재 브랜치를 확인한다. 미커밋 변경이 있으면 보존하고 사용자에게 처리 방향을 묻는다.
5. 원격 최신 `main`을 확인하고 `git-workflow` 스킬 3장으로 브랜치명을 정한다. 기존 브랜치 여부를 확인한다.

## 3. 작업 브리핑 (Phase 2)
1. 모드별 형식으로 작성한다 (QUICK 생략 / STANDARD 3~5줄 계획 / DEEP `behavior-guidelines.md` 5장 구현 브리핑). 브랜치명, **Jira에 반영할 내용**을 포함한다.
   - DEEP 브리핑에 더하는 항목 (STANDARD 계획에는 해당 항목만 한 줄씩): 작업 목적(이슈의 배경/목적), 예상 구현 범위와 구현 방법, 예상 변경 파일(Scene 작업이면 경로 포함, `unity-guidelines.md`), 완료조건, 의존성 및 위험 요소, 사용할 브랜치명(`git-workflow` 스킬 3장), 4장에서 Jira에 반영할 내용(설명 보완 항목, 상태 전환, 이슈 링크 등).
   - 다음 중 하나라도 해당하면 **설계 선택** 항목을 반드시 넣는다: 새 클래스·스크립트 생성, 기존 클래스의 책임 분리·통합, 새 공개 API·이벤트 추가, 상태를 어느 클래스가 가질지 정하는 경우, 프로젝트에서 처음 쓰는 Unity·C# 기능을 쓰는 경우.
     - 대안 2개 이상을 장단점 표로 비교하고 권장안과 이유(최대 3줄)를 적는다.
     - 근거가 되는 기존 구조를 같은 폴더(계층)와 다른 폴더의 예를 함께 확인해 `파일:줄`로 적는다. 한쪽 예만 보고 정하지 않는다.
     - 기획서의 기능 명세(예: I-F4) 하나를 그대로 클래스 하나로 옮기지 않는다. 기획서가 구조를 개발 이슈에 맡긴 경우 구조는 이 비교로 정한다.
     - 이 비교는 기술문서 "대안 비교" 장(`write-tech-doc`)에 그대로 옮겨 쓴다.
2. 범위가 하나의 이슈로 크면 Sub-task 생성 또는 이슈 분리를 제안한다. 승인되면 1단계로 돌아가 이슈를 정리한다.
3. 계획 수립만 요청받았다면 같은 내용을 계획으로 제시하고 멈춘다.
4. DEEP이거나 `behavior-guidelines.md` 5장의 사전 승인 조건에 해당하면 명시적 승인을 기다린다. **Jira 쓰기는 모드와 무관하게 승인 전 하지 않는다.**

## 4. Jira 업데이트 및 검수 (Phase 3)
1. 승인받은 항목만 Jira에 반영한다 (설명 보완은 `issue-template.md`). 상태 전환은 전환할 상태를 제안하고 사용자가 직접 한다.
2. 이슈를 다시 조회해 실제 반영 내용을 보고하고 사용자 검수를 받는다. 수정 요청이 있으면 반영 후 다시 검수받는다.
3. 검수가 끝나면 5장 브랜치 준비로 넘어간다.
- 브리핑에 없던 Jira 변경이 필요해지면 별도로 승인받는다.

## 5. 브랜치 준비
브랜치 생성은 사용자가 직접 한다. Claude는 생성해도 안전한지 먼저 판단하고 결과와 명령을 제시한다.
1. 안전 판단: 다음을 조회해 각 항목의 결과를 보고한다. 하나라도 걸리면 "생성 보류"와 사유·처리 방법을 제시하고, 사용자가 처리한 뒤 다시 판단한다.
   - 미커밋 변경: `git status`에 변경이 없다. 있으면 새 브랜치로 따라가므로 처리 방향(커밋·보관)을 사용자에게 묻는다.
   - 현재 브랜치: 이전 이슈 브랜치에 Push하지 않은 커밋이 없다.
   - 최신 `main`: `git fetch origin` 후 로컬 `main`이 `origin/main`과 같거나 fast-forward로 따라잡을 수 있다.
   - 브랜치명: 같은 이름의 브랜치가 로컬·원격에 없다 (`git-workflow` 스킬 3장).
2. 안전하면 브랜치명과 명령을 제시한다. 예:
   ```bash
   git switch main
   git pull --ff-only origin main
   git switch -c RSP-xx-rhythm-system-design
   ```
   명령은 예시다. 현재 Git 상태에 맞게 조정한다.
3. 사용자가 완료를 알리면 현재 브랜치를 확인하고, `main`과 차이 및 충돌 위험을 보고한다. 승인 없이 merge/rebase하지 않는다.

## 6. 업무 수행으로 전환 (Phase 4~)
- 확정된 범위에서만 구현하고 `behavior-guidelines.md` 7장 기준으로 검증한다. 요청이 계획 수립뿐이면 구현하지 않는다.
- 범위가 바뀌면 `jira-workflow` Phase 5를 따른다.
- 이후 절차는 `jira-workflow` Phase 6~11과 `create-pr`, `write-tech-doc` 스킬을 따른다.

## 마무리
- `behavior-guidelines.md` 8장 형식으로 Jira 키/제목, Jira 반영 내용, 조회한 문서, 브랜치명, 계획, 남은 질문을 보고한다.

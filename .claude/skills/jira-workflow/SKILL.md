# Jira 정책 및 개발 작업 워크플로우

> 이슈 작성 형식은 `issue-template.md`(같은 폴더), Git 세부 규칙은 `git-workflow` 스킬, 브리핑·실행 모드·승인 규칙은 `behavior-guidelines.md` 4·5장을 따른다. 이 문서는 단계와 승인 시점만 정의한다.

## 1. 기본 정책
- Jira 이슈 키는 `RSP-<번호>`다. 브랜치명(`RSP-87-core-rule-design`)과 혼동하지 않는다.
- Atlassian MCP가 인증되어 있을 때 실제 이슈의 제목, 유형, 설명, 완료조건, 상태, 의존성을 조회한다.
- 접근 실패 시 이슈 내용을 추측하지 않고 작업을 멈춘 뒤 사용자에게 알린다.
- 이슈 범위 밖의 변경을 임의로 추가하지 않는다.
- 사용자 승인 없이 이슈 생성, 설명·담당자·스프린트·우선순위·추정치·상태 변경, 이슈 링크 추가를 하지 않는다.
- 이슈 생성·설명 수정에는 `issue-template.md`를 적용한다.
- 도구가 반환한 실제 이슈 키·상태·URL만 보고한다. 상태 전환은 가능한 전환 목록을 조회한 뒤 수행한다.
- **조회 최소화:** 한 세션에서 이미 조회한 이슈는 쓰기 직후 확인이 필요한 경우를 제외하고 다시 조회하지 않는다. 필요한 필드만 요청한다. Confluence는 이 워크플로우만으로는 조회하지 않는다.

## 2. 적용 범위
- **적용:** 기능 구현, 버그 수정, 리팩토링, Unity 에셋·Scene·Prefab 변경 등 프로젝트 파일을 변경하는 개발 작업.
- **예외:** 코드 분석·설명, 읽기 전용 검토, 질문 답변, 단순 오타 수정, 규칙·문서 파일 정리.
- 예외 여부가 불분명하면 사용자에게 Jira 워크플로우 적용 여부를 확인한다.

## 3. 전체 흐름
**Jira 이슈 확인 → 작업 브리핑 → Jira 업데이트 → 업무 수행 → 결과 검수 → 결과 Jira 업데이트 → Commit/Push → PR → 기술문서 업데이트 여부 확인 → Jira 완료 처리**

| 단계 | 진행 조건 (사용자 승인) | 되돌아가는 경우 |
|---|---|---|
| 1. 이슈 확인 | 신규 이슈 생성 시 생성 승인 | — |
| 2. 작업 브리핑 | 브리핑 승인 (Jira 반영 예정 내용 포함) | 범위가 크면 → 1단계(하위 이슈 분할) |
| 3. Jira 업데이트 | 업데이트된 이슈 내용 검수 | 검수 중 수정 요청 → 3단계 반복 |
| 4. 업무 수행 | — | 범위 변경 → 5단계 → 3단계 |
| 6. 결과 브리핑 | 결과 검수 승인 | 수정 요청 → 4단계 |
| 7. 결과 Jira 업데이트 | 6단계 승인 범위 내 | 업무 수정사항 발생 → 4단계 |
| 8~9. Commit / Push / PR | 커밋·Push·PR 진행 승인 | 검증 실패 → 4단계 |
| 10. 기술문서 | 작성·갱신 여부 및 게시 승인 | — |
| 11. 완료 처리 | 완료 조건 충족 + Done 전환 승인 | 미충족 → 사유 보고 후 보류 |

**실행 모드와의 관계** (`behavior-guidelines.md` 4·5장):
- **DEEP:** 위 단계를 그대로 따른다. 2단계 승인 전에는 Jira 쓰기, 브랜치 생성, 파일 수정을 하지 않는다.
- **QUICK/STANDARD:** 2단계 브리핑은 모드별 형식(QUICK 생략, STANDARD 3~5줄 계획)으로 대체하고, 파일 수정·브랜치 생성 시점은 `behavior-guidelines.md` 5장을 따른다. **Jira 쓰기는 모드와 무관하게 승인 전 하지 않는다.** 3단계 Jira 반영 승인을 받기 전 구현을 진행했다면 Jira 반영 예정 내용을 6단계 결과 보고에 함께 제시한다.

## 4. 단계별 절차

### Phase 1. 사용자 명령 및 Jira 이슈 확인
1. 명령에 이슈 키가 있으면 해당 이슈를 조회한다.
2. 이슈 키가 없으면 명령 내용을 기준으로 관련 기존 이슈를 JQL로 검색하고, 후보가 있으면 사용자에게 제시해 대상 이슈를 확인받는다.
3. 관련 이슈가 없으면 **사용자 명령을 기준으로 신규 이슈를 생성할지** 확인한다.
4. 신규 생성 시 `issue-template.md`로 초안을 작성한다. 배경/목적을 확인할 수 없으면 질문하고, 확인 전에는 생성하지 않는다.
5. 초안을 보여주고 승인받은 뒤에만 생성한다. 생성 후 실제 이슈 키를 보고한다.

### Phase 2. 작업 내용 브리핑
DEEP는 `behavior-guidelines.md` 5장의 구현 브리핑 형식에 다음 항목을 더한다 (STANDARD 계획에는 해당 항목만 한 줄씩).
- 작업 목적 (이슈의 배경/목적)
- 예상 구현 범위와 구현 방법
- 예상 변경 파일 (Scene 작업이면 경로 포함, `unity-guidelines.md`)
- 완료조건
- 의존성 및 위험 요소
- 사용할 브랜치명 (`git-workflow` 스킬 3장)
- **3단계에서 Jira에 반영할 내용** (설명 보완 항목, 상태 전환, 이슈 링크 등)

작업 범위가 하나의 이슈로 다루기 크면 하위 이슈(Sub-task) 생성 또는 이슈 분리를 제안하고, 승인되면 Phase 1로 돌아가 이슈를 정리한다.

### Phase 3. 작업 내용 Jira 업데이트
1. 브리핑에서 승인받은 항목만 Jira에 반영한다.
   - 목표·작업 범위 확정, 작업 내용 반영, 완료조건 보완 (`issue-template.md`)
   - 관련 이슈 연결
   - 필요 시 진행 상태 전환 (예: 진행 중)
2. 반영 후 이슈를 다시 조회해 실제 반영된 내용을 사용자에게 보고하고 **검수**받는다.
3. 검수가 끝나면 `git-workflow` 스킬에 따라 최신 `main`에서 기능 브랜치를 준비한다.

브리핑에 없던 Jira 변경이 필요해지면 별도로 승인받는다.

### Phase 4. 업무 수행
- 확정된 범위 안에서만 작업한다. 기존 코드·구조를 우선하고 불필요한 추상화와 범위 확장을 하지 않는다.

### Phase 5. 작업 범위 변경 처리
작업 중 추가 요구사항이나 예상하지 못한 문제가 생기면 작업을 멈추고 다음을 따른다.
1. 변경사항과 원인을 확인한다.
2. 기존 Jira 이슈 범위에 포함되는지 판단한다.
3. 범위를 벗어나거나 커지면 신규 이슈 또는 Sub-task 분리를 제안한다.
4. 변경 범위·영향·Jira 반영 내용을 브리핑하고 승인받는다.
5. 승인된 내용을 Jira에 반영한다 (Phase 3 절차, 신규 이슈면 Phase 1 절차).
6. 변경된 범위로 Phase 4를 재개한다.

**사용자 승인 없이 새로운 작업을 추가하지 않는다.**

### Phase 6. 작업 결과 브리핑 및 사용자 검수
`behavior-guidelines.md` 8장 형식으로 보고하되 다음을 포함한다.
- 구현된 기능, 생성 / 수정 / 삭제 파일
- 구현된 기능에 따라 생성 및 수정된 파일의 핵심 부분 설명(자세한 위치 포함)
- 완료조건별 충족 여부 (검증 / 미검증 구분)
- Unity 검증 결과 (컴파일, Console 로그, Play Mode 등 실제 수행한 것만)
- 미완료 사항

사용자 검수 승인 전에는 Commit / Push를 하지 않는다. 수정 요청이 있으면 Phase 4로 돌아가 수정한 뒤 다시 검수받는다.

### Phase 7. 작업 결과 Jira 업데이트
검수 승인 후 실제 결과를 Jira에 반영한다 (코멘트 또는 설명 보완).
- 실제 구현 내용과 변경 파일
- 완료조건 검증 결과 (검증한 항목만 체크)
- 해결된 문제, 남은 작업

반영 내용은 6단계에서 보고·검수된 사실에 한정한다. 이 시점에 업무 수정사항이 생기면 Phase 4로 돌아간다.

### Phase 8. Commit / Push
- `git-workflow` 스킬과 `create-pr` 스킬을 따른다 (브랜치명, 커밋 메시지, 관련 파일만 stage).
- 사용자가 커밋·Push를 요청하거나 승인한 경우에만 수행한다.

### Phase 9. Pull Request
- `git-workflow` 스킬 5장에 따라 기능 브랜치 → `main` PR을 생성하고 PR 제목·본문에 Jira 이슈를 연결한다.
- PR 생성과 병합은 별개다. Claude는 PR을 병합하지 않는다.
- 생성된 PR URL을 Jira 이슈에 코멘트로 남길지는 Phase 2 또는 Phase 7 승인 범위에 따른다.

### Phase 10. 기술문서 업데이트 여부 확인
PR 생성 후 관련 문서의 갱신 필요 여부를 판단해 사용자에게 질문한다. 예: "이번 변경사항을 Confluence 기술문서에 신규 작성하거나 반영할까요? Jira 문서화 이슈도 생성할까요?"
- 대상: Confluence 기술문서, 시스템 설계 문서, 데이터 인터페이스 문서, 기존 구현 설명, 다이어그램
- 필요하면 변경 계획을 브리핑하고 승인 후 `write-tech-doc` 스킬로 작성·갱신한다.
- 불필요하면 사유를 사용자에게 보고하고, 승인 시 Jira 코멘트로 기록한다.
- Jira 문서화 이슈는 사용자에게 먼저 묻고 승인받은 경우에만 생성한다.

### Phase 11. Jira 완료 처리
다음을 모두 확인한다.
- [ ] 작업 범위 구현 완료
- [ ] 완료조건 검증 (미검증 항목 없음)
- [ ] 사용자 결과 검수 완료
- [ ] Commit / Push 완료
- [ ] PR 생성 및 `main` 병합 여부 확인 (`gh`로 실제 상태 조회)
- [ ] 기술문서 업데이트 완료 또는 불필요 확인

모두 충족하고 사용자가 Done 전환을 승인하면 가능한 전환을 조회해 완료 처리한다. **PR 생성만으로 Done 처리하지 않는다.** PR이 아직 병합되지 않았거나 다른 항목이 미충족이면 완료 처리하지 않고 미충족 항목과 사유를 보고한다.

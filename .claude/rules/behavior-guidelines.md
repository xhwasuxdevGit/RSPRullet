# Claude Code 공통 행동 지침 (상시 로드)

> 매 세션 자동 로드되는 핵심 규칙이다. 작업별 상세 지침은 해당 작업에서만 로드한다 (`CLAUDE.md` "지침 위치").

## 1. 사고 우선 (Think Before Coding)
- 가정을 명시하고, 불확실하면 질문한다. 해석이 여러 갈래면 선택지를 제시하고 임의로 고르지 않는다.
- 더 단순한 방법이 보이면 알린다.
- 코드를 읽기만 하고 세운 결론은 **미검증**으로 표기한다.

## 2. 단순함 우선 (Simplicity First)
- 요청 범위 밖 기능, 한 번만 쓰는 추상화, 요청하지 않은 확장성, 발생할 수 없는 상황의 예외 처리를 만들지 않는다.
- 불필요한 클래스, 인터페이스, 빈 메서드, 미사용 변수를 만들지 않는다.

## 3. 외과적 변경 (Surgical Changes)
- 인접 코드·주석·포맷을 임의로 개선하거나 정상 코드를 리팩토링하지 않는다.
- 이번 변경으로 미사용이 된 코드는 정리하고, 기존 미사용 코드는 보고만 한다.
- 요청·승인 범위 밖 파일은 수정하지 않는다. 다른 파일의 문제는 보고만 한다.
- 기존 사용자 변경사항을 폐기하지 않는다. Scene, Prefab, `.meta`, GUID 연결을 보존한다.

## 4. 실행 모드
사용자가 모드를 지정하면 따른다. 지정이 없으면 영향도로 선택하고 기본값은 **STANDARD**다. 위험한 변경은 QUICK으로 처리하지 않는다.

| 모드 | 대상 | 조사 | 검증 | 보고 |
|---|---|---|---|---|
| QUICK | Jira 설명·상태, Confluence 일부 수정, 주석·문구, 작은 설정, 단순 코드 수정 | 관련 파일·이슈만 | 변경 내용·Diff 확인 (필요 시 컴파일) | 5~10줄 |
| STANDARD | 일반 C# 기능, 기존 State 내부 로직, UI Prefab, 1~3개 시스템 연결 | 수정 파일 + 직접 호출 관계 | 영향 EditMode 테스트, Scene 변경 시 해당 Scene | 10~20줄 |
| DEEP | 게임 핵심 구조, 코어 규칙 변경, 딜러의 AI 설정과 관련된 작업, 시스템 간 계약, 대규모 리팩터링 | 전체 영향 범위 + 관련 기술문서 | 관련 테스트 + 전체 EditMode 회귀(마지막 1회) | 상세 |

## 5. 구현 착수와 승인
- **QUICK:** 명확한 경량 작업은 설계 승인 없이 진행한다.
- **STANDARD:** 3~5줄 작업 계획(변경 파일·방법·검증)과 번호 붙인 작업 단계(생성/수정 파일 단위, Scene·Prefab 배치와 검증은 각각 별도 단계)를 제시하고, 설계 선택이나 위험이 없으면 같은 턴에서 바로 구현한다. 설계 선택이 있으면 DEEP 브리핑의 **설계 선택** 항목을 넣고 승인 후 구현한다. 이 단계가 8장 중간 보고의 단위다.
  - 단계는 위험도로 묶는다. 기존 흐름에 연결되지 않는 작업(설정 값 추가, 새 클래스 작성, 주석·문구)은 한 단계로 묶는다.
  - 게임 흐름·상태 기계·데이터 계약 변경, Scene·Prefab 변경, Play 검증은 각각 별도 단계로 둔다.
- **DEEP:** 아래 형식의 구현 브리핑을 작성하고 **명시적 승인 후** 구현한다.
- STANDARD라도 다음에 영향을 주면 **사전 승인 필수**: 게임 흐름 구조와 상태 기계 관련, 데이터 계약(SO·이벤트 시그니처 등), 기존 공개 API·직렬화 필드 호환성.
- 작업 중 범위가 커지거나 바뀌면 멈추고 이유·영향을 설명한 뒤 승인받는다. 사용자 정정으로 계획이 바뀌면 남은 단계를 다시 번호 붙여 밝힌 뒤 진행한다.
- Play 검증 단계는 사용자가 수행하고 Claude는 방법을 제시한다. 확인할 상황이 확률적이거나 반복이 필요하면 브리핑 작업 순서에 미리 안내한다 (`unity-guidelines.md` 4장).

모드와 무관하게 **항상 승인이 필요한 작업**:
- PR 생성, PR 병합 (병합은 Claude가 하지 않는다)
- Jira 쓰기(생성·설명·담당자·스프린트·링크), Confluence 쓰기
- 강제 Push, `reset --hard`, `clean`, 브랜치 삭제, 기존 변경 폐기, 배포 설정 변경
- `Assets/Scenes/Main/` 수정, 패키지·Assembly Definition 추가

**사용자가 직접 수행하는 작업** (Claude는 초안만 준비하고, 사용자가 완료를 알리면 조회로 확인한다):
- 기능 브랜치 생성: 브랜치명
- Jira 상태 전환: 전환할 상태
- Jira 코멘트 게시: 코멘트 본문 초안
- Commit·Push: stage할 파일 목록과 커밋 메시지 초안

DEEP 브리핑 형식:
```text
## 구현 브리핑: [기능명]
**작업 범위** (요약)
**생성/수정 파일** - 생성/수정: 경로 (역할·변경 내용) / Scene 작업이면 Scene 경로 포함
**설계 선택** 새 클래스·책임 분리·공개 API·상태 소유·처음 쓰는 기능이 바뀌면 대안 비교 표 + 기존 구조 근거(`파일:줄`) + 권장안. 해당 없으면 "해당 없음: 이유"
**작업 순서** 1. [단계] → 확인: [검증 항목] (각 단계가 8장 중간 보고의 단위)
진행할까요?
```

## 6. 조사 범위
- **코드:** 수정 대상과 그 연결 지점(호출자·피호출자, 새 코드가 값·상태를 넘길 기존 코드)만 필요한 메서드·라인 단위로 본다. 연결 지점은 기능 키워드 검색으로 먼저 찾고, 전체 저장소 탐색은 그래도 못 찾을 때만 한다.
- **Jira:** 지정 이슈부터 조회한다. 관련 이슈는 실제 의존성이 있을 때만, Epic·Sprint는 변경이 필요할 때만 본다. 프로젝트 전체 이슈 목록을 조회하지 않는다.
- **Confluence:** 이슈와 무관한 작업에서는 조회하지 않는다. 개발 이슈는 `start-issue` 2-2 기준으로 관련 문서만 조회한다.
- **Git/GitHub:** 작업 시작 시 브랜치·Working Tree만 확인한다. PR 생성·갱신 시 필요한 상태만 재확인한다. 요청 없는 히스토리 전체 조사는 하지 않는다.
- **공통:** 이미 확인한 내용·이슈·PR 상태를 반복 조회하지 않는다. 같은 정보를 여러 도구로 중복 조회하지 않는다. 가능하면 최소 응답 필드를 쓴다. 도구 실패 시 수정된 입력으로 1회만 재시도하고 그래도 실패하면 보고한다.

## 7. 검증 정책
| 작업 유형 | 기본 검증 |
|---|---|
| Jira/문서 변경 | 변경 내용 재확인 |
| 주석/문구 수정 | Diff 확인 |
| 작은 C# 수정 | 컴파일 (동작이 바뀌면 관련 테스트) |
| 코어 규칙 관련 로직 수정 | 관련 EditMode 테스트 |
| 게임의 전체 흐름 구조, 상태 기계, 딜러 AI 로직 변경 | 관련 테스트 + 전체 EditMode 회귀(마지막 1회) |
| UI/Prefab/Scene 변경 | 영향받는 Scene Play 검증 (사용자 수행, Claude는 방법 제시) |
| 플랫폼 관련 변경 | 해당 플랫폼 컴파일/빌드 |

**테스트 실행 범위와 시점**
- "관련 테스트"는 수정한 클래스를 직접 검증하는 테스트 클래스만 `--filter`로 실행한다.
- 전체 EditMode 회귀는 이슈당 1회, 마지막 구현 단계가 끝난 뒤(또는 `create-pr` 검증 시)에만 실행한다. 중간 단계에서는 실행하지 않는다.
- 이미 통과한 뒤 코드가 바뀌지 않은 테스트는 다시 실행하지 않고 결과를 재사용한다.
- 주석·문구·Scene·Prefab·에셋만 바꾼 단계는 테스트를 실행하지 않는다. C# 파일을 바꿨으면 컴파일만 확인한다.

- 실행하지 않은 검증은 **미실행**으로 표기한다. 실패한 테스트를 무시하지 않는다. 도구로 확인하지 않은 빌드·PR URL·Jira 상태를 만들어내지 않는다.

## 8. 보고
- **중간 보고:** 브리핑에서 제시한 단계가 끝날 때마다 아래 `[작업 결과]` 블록 전체를 그 턴의 마지막 메시지로 보내고 멈춘다. 사용자가 확인하거나 진행을 지시한 뒤에 다음 단계의 첫 도구를 부른다.
  수행한 작업 내용과, 브리핑에서 밝힌 의도대로 수행되었는지(달라진 점이 있으면 그 이유)를 쓴다.
    - 한 줄 진행 알림, 여러 단계를 마지막에 묶은 보고는 중간 보고로 인정하지 않는다.
    - 보고는 이번 단계에서 바뀐 사실과 검증 결과만 쓴다. 이미 보고한 배경, 다음 단계 상자(앱의 마무리 요약)와 같은 내용은 되풀이하지 않는다.
    - 도구 호출 사이에 쓴 텍스트는 사용자에게 보이지 않을 수 있으므로 중간 보고로 인정하지 않는다.
    - Scene·Prefab을 저장했으면 Play 검증 전에 보고한다.
    - 검증 중 결과를 보고 수정(위치·값 조정 등)했으면, 이어서 진행하기 전에 무엇을 왜 바꿨는지 바로 보고한다.
    - 앱의 작업 목록(할 일 표시)을 쓰는 환경이면 목록 항목을 브리핑 단계와 1:1로 맞추고, 다음 항목으로 넘기기 전에 보고한다.
- **자주 빠지는 확인 (상시)**
    - 단계가 끝나면 `[작업 결과] N단계` 블록을 턴의 마지막 메시지로 보내고 멈춘다. 같은 턴에서 다음 단계로 넘어가지 않는다.
    - `main`을 당기거나 브랜치를 바꾼 뒤 `.claude/`·`CLAUDE.md`가 바뀌었으면 다시 읽고 진행한다.
    - `unity` 명령은 `timeout 60`으로만 실행하고, 124면 멈춘 뒤 사용자가 처리했다고 말할 때까지 기다린다 (`unity-guidelines.md` 8장).
```text
[작업 결과] N단계: [단계 이름]
- 변경: ...
- 핵심 변경: 무엇을 어떻게 바꿨는지와 정확한 위치 (구현 작업일 때). 코드는 수정 후 기준 `파일:줄 번호`, Scene·Prefab은 계층 경로와 바꾼 필드·값으로 적는다.
- 검증: ...
- 주의/미검증: ...
- 다음 단계: ...
```
- 변경 파일, 테스트 결과, 예외사항 중심으로 쓴다. 이미 제공한 배경·아키텍처를 반복하지 않는다. 같은 질문을 반복하지 않는다.

## 9. Subagent와 세션 나누기
- 병렬 조사가 실제로 유리하거나, 독립적인 대규모 분석·복잡한 다중 시스템 검증이거나, 사용자가 명시적으로 요청한 경우에만 쓴다.
- 단순 Jira 조회, 문서 수정, 작은 코드 변경은 직접 수행한다.
- 세션은 이슈 처리 구간별로 나눈다. 대화가 길수록 API 호출마다 대화 전체를 다시 읽어 비용이 커진다.
  - 착수 세션: `start-issue`(조사·브리핑 승인·Jira 반영·브랜치 준비)까지. 끝나면 구현을 새 세션으로 넘긴다. 인계 내용: Jira 키, 브랜치명, 승인된 브리핑 전문, 구현에 필요한 기획서 값과 `파일:줄`.
  - 구현 세션: 구현·검증·PR까지.
  - 구현 세션에서 사용자 입력이 약 25회를 넘었는데 남은 단계가 있으면, 현재 상태와 남은 단계를 인계해 새 세션으로 나누자고 제안한다.
- PR 생성(문서 변경 메모 작성 포함)까지는 구현 세션에서 하고, 기술문서 작성·갱신(`jira-workflow` Phase 10)은 별도 세션에서 수행한다. 새 세션에는 Jira 키, PR 번호, 문서 변경 메모 위치, 기획서와 다르게 정한 값과 이유를 넘긴다.

## 10. 응답 및 코드 작성
- 소스코드 주석은 한국어로 작성한다. C# 규칙은 `coding-conventions.md`(C# 파일 작업 시 자동 로드)를 따른다.
- 실제 검증한 결과와 추론한 내용을 구분한다.

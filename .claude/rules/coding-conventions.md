# C# 코딩 컨벤션

## 1. 기본 원칙
- 새로운 패턴을 도입하기보다 가독성, 작은 변경, 인접 코드와의 일관성을 우선한다.
- 단순 기능을 위해 내부 클래스, `sealed` 클래스, 불필요한 인터페이스, 범용 프레임워크 또는 계층을 추가하지 않는다.
- Unity 직렬화나 Inspector 연동이 실제로 필요하지 않은 일시적 런타임 로직은 순수 C# 클래스를 우선 검토한다.
- 매직 넘버를 피하고 의미 있는 상수 또는 명시적인 설정으로 관리한다.
- 입문자가 읽고 고칠 수 있는 수준으로 쓴다.
  - 프로젝트에서 처음 쓰는 Unity·C# 기능(속성(attribute), 실행 순서·초기화 콜백, 리플렉션, async/코루틴 신규 도입, 제네릭 제약 등)은 기존 코드에서 같은 기능을 쓰는 예를 먼저 검색한다. 예가 없으면 구현 브리핑의 설계 선택에 더 쉬운 대안과 비교해 적고 승인받은 뒤 쓴다.
  - 에디터·프로젝트 설정에 따라 동작이 달라지는 코드는 `ProjectSettings/`에서 현재 설정 값을 먼저 확인한다. 현재 설정에서 필요 없는 대비 코드는 만들지 않는다.

## 2. 네이밍
- 타입, 공개 멤버, 메서드: `PascalCase`
- 매개변수, 지역 변수: `camelCase`
- 비공개 필드: `_camelCase` (기존 코드에 다른 일관된 규칙이 있으면 해당 규칙을 우선 확인)
- 의미가 드러나는 이름을 사용하고 모호한 축약어를 피한다.

## 3. 구현 규칙
- 가능한 범위에서 클래스와 메서드의 책임을 명확하게 분리한다.
- 깊은 중첩보다 조기 반환(early return)을 우선한다.
- 기존 공개 API와 직렬화 필드명을 보존한다. 직렬화 필드명 변경은 Scene/Prefab 연결을 깨뜨릴 수 있다.
- `Update()`처럼 자주 호출되는 경로에서 불필요한 할당이나 비용이 큰 조회를 피한다.
- 화면 갱신은 상태가 바뀔 때 이벤트로 받는 방식을 우선한다. `Update()`에서 매 프레임 상태를 읽는 방식은 시간 측정처럼 프레임마다 처리해야 하는 경우나 필요한 이벤트가 아직 없는 경우에만 쓰고, 그 이유를 주석에 남긴다.
- 이벤트 구독은 수명 주기에 맞춰 해제한다.
- 주석은 모든 코드를 설명하기보다 설계 의도, 불변 조건, 이해하기 어려운 타이밍 로직에 작성한다.
- 주석은 내부 원리 용어(도메인 리로드, 직렬화 콜백 순서 등) 대신 눈에 보이는 동작으로 쓴다. 예: "static 값은 씬을 다시 불러와도 남고, Play를 새로 시작하면 처음 값으로 돌아간다". 동작이 설정에 달려 있으면 Unity 메뉴 경로(`Project Settings > Editor > …`)로 적는다.
- 주석에서 문서를 참조할 때는 문서 이름을 줄이지 않고 그대로 적고, 장 번호·기능 번호·예외 번호만 단독으로 쓰지 않는다. 같은 주석 안에서 두 번째 참조부터도 문서 이름을 붙인다. 예: `(4-4장 예시 ②)` → `(코어 규칙 상세 기획서 4-4장 정산 예시 ②)`, `(예외 E4)` → `(코어 규칙 상세 기획서 6장 예외 E4)`
- 주석 본문에는 기획서의 화면·상태 번호(예: `판-07`, `종료-01`)나 기획서에서만 쓰는 용어를 그대로 쓰지 않고, 코드의 이름이나 그 스크립트만 읽어도 알 수 있는 말로 쓴다. 번호는 문서 참조 괄호 안에서 위치를 가리킬 때만 쓴다. 예: `// 판-07 승패 판정 표시를 기다리는 중인지` → `// 판 결과를 보여 주는 중인지`

## 4. 검증
- 컴파일 오류, null 처리, 유니티 라이프 사이클을 확인한다.
- 저장소의 기존 테스트 구성과 호환되고 실효성이 있을 때 테스트를 추가한다.
- 실제로 실행하고 확인하지 않은 Unity 컴파일이나 빌드를 성공했다고 보고하지 않는다.
